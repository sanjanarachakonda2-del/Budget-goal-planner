```text

```

Folder rules:

- The frontend directory MUST be named `frontend`, never `public`.
- The backend directory MUST be named `backend`.
- The database directory MUST be named `database`.
- The root directory MUST contain a complete `README.md`.
- Keep all SQL scripts in `database/`.
- Keep backend routes, middleware, and helper files inside `backend/`.
- Keep frontend HTML, CSS, and browser JavaScript inside `frontend/`.
- Include additional files such as authentication utilities, controllers, validation modules, and tests when necessary.
- Do not create unnecessary files just to fill the folder structure.

Configure Express to serve the frontend correctly from the `frontend/` directory. For example:

```javascript

```

Use the correct absolute paths, imports, asset references, API URLs, and environment variable names throughout the application.

The final folder structure must match the code and the README exactly.

### Database correctness requirements

- Ensure the SQL schema matches every table and column referenced in the backend.

- Prevent duplicate registrations, votes, bookings, or other repeated actions where the project requires uniqueness.
- Handle related record creation and deletion safely.
- Use database transactions or PostgreSQL functions when multiple related changes must succeed together.
- Store dates, times, quantities, monetary amounts, statuses, and calculated values appropriately.
- Calculate important totals and balances on the backend or database rather than trusting values submitted by the browser.
- Provide the complete SQL needed to initialize the database.

## 9. Authentication, Authorization, and Security

Implement security appropriate to the selected project.

If the project requires users to log in, provide a secure authentication system and explain it in simple language.

Choose a consistent approach, preferably Supabase Auth where appropriate, or a carefully implemented server-managed authentication mechanism. Do not mix incompatible authentication approaches.

If using Supabase Auth, explain how user identities connect to application tables and how the backend verifies the authenticated user.

If implementing custom authentication, securely hash passwords using a suitable password-hashing library. Never store passwords in plaintext.

For authenticated applications:

- Protect private API endpoints.
- Enforce role-based permissions on the backend.
- Ensure users can access only the records they are authorized to access.
- Never trust a user ID or role supplied by the browser without verification.
- Prevent users from changing their own roles through ordinary requests.
- Validate all incoming data.
- Keep privileged Supabase keys on the server only.
- Use secure session or token handling.
- Configure cookies appropriately when using cookie-based sessions.
- Apply CSRF protections when required by the authentication design.
- Use appropriate login rate limiting and security headers.
- Avoid exposing sensitive user data in API responses.

Configure PostgreSQL Row Level Security (RLS) and suitable policies where appropriate. Explain how the chosen authentication design interacts with RLS.

**Important:** Never place the Supabase service-role key, secret key, database password, or other privileged credentials in frontend JavaScript, HTML, CSS, GitHub, or public documentation. Server-side privileged database access must be protected by backend authorization checks.

If the project does not require accounts, do not add an unnecessary login system. Protect sensitive administrative operations according to the project's actual requirements.
